# Proposal: KVM backend
 
## Abstract
 
A vmm backend for Linux's KVM, `src/vmm/kvm.zig`, on arm64 and x86\_64. On arm64 it reuses HVF's shim and page tables unchanged. On x86\_64 it adds an amd64 shim, which [whp](0017-whp.md) shares: the host sets up long mode, the descriptor tables and the SYSCALL MSRs directly, and the shim is only the exception and syscall entry, the `OUT` doorbell and the return to user mode. `auto` uses KVM on Linux when `/dev/kvm` is usable, and the suite that passes on HVF and the emulator passes on KVM.
 
## Background
 
This was milestone M8 in DESIGN.md, before milestones became proposals ([#1](0001-proposals.md)).
 
### The vmm contract
 
DESIGN.md's Hypervisor layer was shaped for KVM from the start: the VM is created with `KVM_CREATE_VM`, memory is mapped with `KVM_SET_USER_MEMORY_REGION`, vCPUs run with `KVM_RUN`, and a kick is `immediate_exit` plus a signal to the thread. Access needs read/write on `/dev/kvm`. The portability rules apply:
 
- The shim exits through an MMIO doorbell, since arm64 KVM handles HVC itself unless hypercall filtering is configured, and through `OUT` on x86.
- One large guest-physical region is mapped once, since KVM caps the number of memory slots.
- Guest page tables use 4K pages.
- A vCPU is created, run and destroyed on one host thread.
### h9 today
 
- **`src/vmm/hvf.zig`** (543 lines) holds three things: a guest-physical page allocator over one RAM region, arm64 stage-1 page tables (4K granule, user half under TTBR0, a kernel half under TTBR1 shared by every vCPU, with the shim, the doorbell page and the per-vCPU shared pages), and the HVF calls. Only the last part is HVF's.
- **The arm64 shim** (`src/arch/arm64/shim.S`) is the exception vectors plus an entry at `vectors + 0x800`. The host sets every system register (`VBAR_EL1`, `MAIR_EL1`, `TCR_EL1`, `TTBR0_EL1`, `TTBR1_EL1`, `CPACR_EL1`, `SP_EL1`, `SCTLR_EL1`). It rings the doorbell with a single `str x0, [x1]`, and expects the host to advance the PC past it.
- **amd64** runs only on the emulator. `src/arch/amd64.zig` has the Ureg and 9front's user selectors (`UESEL`, `UDSEL`, from `pc64/mem.h`). 9front's amd64 libc enters the kernel with `SYSCALL`, which the emulator hooks.
- **`vmm.Kind`** is `hvf` and `emu`. `--backend kvm` parses, and `vmm.create` returns `BackendNotBuilt` for it. `--check` probes it and lists it only when asked.
- **The vCPU pool** (`src/cpupool.zig`) uses `maxVcpus` less a reserve of 8 for owned vCPUs.
- **Test VMs:** the Lima `linux` VM (vz, arm64) and `linux-amd64` (QEMU, emulated) have no `/dev/kvm`.
## Proposal
 
### Shared pieces, moved out of `hvf.zig`
 
- **`src/vmm/gphys.zig`:** the guest-physical page allocator, unchanged.
- **`src/vmm/pt_arm64.zig`:** arm64 tables, `pteAttrs`, the TCR, MAIR and SCTLR values, and the kernel-half layout (`kva_shim`, `kva_doorbell`, `kva_shared`).
- **`src/vmm/pt_amd64.zig`** and **`src/vmm/x86.zig`:** new, below. `x86.zig` holds the amd64 CPU state the host sets (control registers, the GDT, TSS and IDT images, the SYSCALL MSRs and the CPUID mask) as plain values, so [whp](0017-whp.md) sets the same state through its own calls.
`hvf.zig` keeps only HVF's calls. That's an internal refactor, with HVF's behaviour unchanged.
 
### The backend
 
`src/vmm/kvm.zig`, built on Linux for aarch64 and x86\_64. It needs no library: its ioctls and structs are declared in `src/vmm/kvm_abi.zig`, so static musl builds keep working.
 
| Step | arm64 | x86\_64 |
| --- | --- | --- |
| Open | `/dev/kvm`, read-write; `KVM_GET_API_VERSION` must be 12 | Same |
| Required capabilities | `KVM_CAP_USER_MEMORY`, `KVM_CAP_IMMEDIATE_EXIT` | Same |
| VM | `KVM_CREATE_VM` with `KVM_VM_TYPE_ARM_IPA_SIZE(36)`, the 36 bits HVF uses, after checking `KVM_CAP_ARM_VM_IPA_SIZE` covers it. The default type asks for 40 bits, which a nested host may not offer | `KVM_CREATE_VM` |
| Memory | One slot: the RAM region at `ram_ipa`, as on HVF | One slot, at the same guest-physical address |
| vCPU | `KVM_CREATE_VCPU`, `mmap` of `kvm_run`, `KVM_ARM_PREFERRED_TARGET` then `KVM_ARM_VCPU_INIT` | `KVM_CREATE_VCPU`, `mmap`, `KVM_SET_CPUID2`, `KVM_SET_SREGS`, `KVM_SET_MSRS` |
| System state | `KVM_SET_ONE_REG` with the same values HVF sets. KVM's system-register IDs use the same op0/op1/CRn/CRm/op2 encoding as HVF's constants | Set by the host: see the amd64 shim |
| Ureg | In the shared page, as on HVF | In the shared page |
| FP/SIMD, thread pointer | `KVM_{GET,SET}_ONE_REG`: `fp_regs.vregs[0..31]`, `fpsr`, `fpcr`, `TPIDR_EL0` | `KVM_{GET,SET}_FPU` (the FXSAVE contents), and `FS_BASE` through `KVM_{GET,SET}_MSRS` |
| Switch address space | `TTBR0_EL1` with `KVM_SET_ONE_REG`, then the shim's flush word, as on HVF | The shared page's next-CR3 word, which the shim loads before returning |
| Doorbell exit | `KVM_EXIT_MMIO` at the doorbell page | `KVM_EXIT_IO`, an `OUT` to the doorbell port |
| vCPU limit | `maxVcpus`: `KVM_CHECK_EXTENSION(KVM_CAP_MAX_VCPUS)` on the VM, capped by the file descriptors left (see vCPU lifetime) | Same |
 
**The doorbell's PC.** HVF reports the doorbell store as an exception and leaves the PC on it, so `hvf.zig` advances it. KVM completes an MMIO or port I/O exit itself on the next `KVM_RUN`, so the KVM backend doesn't touch the PC. The arm64 shim's `str x0, [x1]` is a single-register store, so its data abort has a valid syndrome (ISV), which KVM needs to hand it to userspace as `KVM_EXIT_MMIO`.
 
**Other exits:** `KVM_RUN` failing with `EINTR`, or returning `KVM_EXIT_INTR`, is `.interrupted`. Everything else, such as `KVM_EXIT_FAIL_ENTRY` or `KVM_EXIT_INTERNAL_ERROR`, is `.other` with the exit reason, which `--dump-on-fault` prints.
 
**No interrupt controller.** h9 never injects interrupts, so no in-kernel irqchip is created. The guest never enables a timer.

### vCPU lifetime

KVM can't destroy one vCPU. Closing its fd drops a reference, but the vCPU lives until the VM is destroyed, and `KVM_CREATE_VCPU` fails once the number ever created reaches the limit. On HVF a destroyed vCPU frees its slot, and the vCPU pool counts on that: without recycling, KVM's limit would cap the processes a machine runs over its life, not the ones alive at once.

So `kvm.zig` keeps a free list:

- `destroyVcpu` parks the vCPU on the list instead of closing it.
- `createVcpu` takes a parked vCPU first, and calls `KVM_CREATE_VCPU` only when the list is empty. A reused vCPU is reset: `KVM_ARM_VCPU_INIT` again and the system registers on arm64, which KVM documents as a full reset; on x86, which has no reset call, the registers, sregs, FPU state and MSRs are all set again. `immediate_exit` is cleared, and the calling thread is recorded for `kick`.
- KVM doesn't bind a vCPU to the thread that created it, so a parked vCPU can be taken by any thread. HVF's rule, that a vCPU is created, run and destroyed on one thread, still holds from the caller's side.
- The vmm interface doesn't change.

Each vCPU holds a file descriptor, and its `kvm_run` mapping. The usual soft `RLIMIT_NOFILE` of 1024 is below x86's vCPU limit, so the backend raises the soft limit to the hard one when the VM is created, and `maxVcpus` reports the smaller of KVM's limit and what the descriptors left allow, keeping a margin for drawterm's own files.
 
### Kicks
 
`kick` sets `kvm_run.immediate_exit` and sends the vCPU's thread a signal. The signal is `SIGRTMIN + 1`, reserved by h9:
 
- It's blocked in every h9 thread: the mask is set before the kernel boots, so every thread inherits it.
- Each vCPU passes `KVM_SET_SIGNAL_MASK` a mask with it unblocked, so it can arrive only inside `KVM_RUN`. Host syscalls elsewhere in h9 and drawterm never see a spurious `EINTR`.
- Its handler does nothing.
A kick that comes before `KVM_RUN` is caught by `immediate_exit`, and one that comes during it interrupts it. Either way `run` returns `.interrupted` and clears `immediate_exit`. The thread is recorded at `createVcpu`, which runs on the thread that will run the vCPU.
 
### The amd64 shim
 
`src/arch/amd64/shim.S`, assembled freestanding and embedded as `shim_arm64` is. The host sets up the CPU state the shim would otherwise set up, as HVF does on arm64:
 
- **Control and mode:** `CR0` (`PE`, `MP`, `ET`, `NE`, `WP`, `PG`), `CR4` (`PAE`, `OSFXSR`, `OSXMMEXCPT`, plus `SMEP` and `SMAP` when the CPU has them), and `EFER` (`LME`, `LMA`, `SCE`, `NXE`), with `KVM_SET_SREGS`.
- **Descriptor tables,** written by the host into kernel pages: one GDT per vCPU, laid out as 9front's `pc64` is, so `UESEL` and `UDSEL` are the user selectors, with a 64-bit TSS whose `IST1` points at the vCPU's save area. One IDT, shared, with every vector 0 to 31 going through `IST1`.
- **SYSCALL:** `STAR` (kernel `CS`), `LSTAR` (the shim's syscall entry), `SFMASK` (clears `IF`, `TF`, `DF` and `AC`), and `KERNEL_GS_BASE`, the vCPU's shared page, with `KVM_SET_MSRS`.
- **CPUID** from `KVM_GET_SUPPORTED_CPUID`, with `XSAVE`, `OSXSAVE` and AVX cleared, so user code uses only state the FXSAVE image carries.
The shim itself does three things:
 
1. **Syscall entry** (`LSTAR`): `swapgs`, save the user `RSP` and every register into the shared page's Ureg, set `type` to 64 as the emulator and 9front do, and ring the doorbell with `OUT`.
2. **Exception entry** (IDT vectors 0 to 31): save the Ureg, with the vector in `type`, the error code in `error` and, for a page fault, `CR2` in the fault address, and ring the doorbell.
3. **Return:** if the shared page's next-CR3 word is set, load it into `CR3` and clear it, which also flushes the TLB. Then restore the Ureg, possibly changed by the host, `swapgs`, and `iretq` to user mode.
Returning with `iretq` rather than `sysretq` gives one path for syscalls, faults and notes, and sidesteps `sysret`'s non-canonical `RCX` trap.
 
**Page tables** (`pt_amd64.zig`): 4-level, 4K pages, `U/S` for user pages and `NX` for non-executable ones. The kernel half sits at the top of the address space, as on arm64, under PML4 entry 511. x86 has one root, so every address space's PML4 shares entry 511 with the kernel's, and the shim, IDT and per-vCPU pages are mapped supervisor-only there.
 
### Selection and `--check`
 
- `vmm.Kind` gains `kvm`. `vmm.create(.kvm)` creates it, and `auto` tries it first on Linux, falling back to the emulator on `HypervisorUnavailable`, as on macOS.
- **Errors:** `/dev/kvm` missing, or `EACCES` on it, is `HypervisorUnavailable`. `tools.explain` says which: "no /dev/kvm (no KVM in this kernel, or a VM without nested virtualization)", or "no access to /dev/kvm (is your user in the kvm group?)".
- **`--check`** reports KVM with its vCPU limit, as for HVF.
- **The vCPU pool** uses KVM's limit less the reserve, as for HVF. Recycling makes the limit one on live vCPUs, as HVF's is.
### Test VMs
 
`scripts/lima/` gains a `linux-kvm` instance: vz with Lima's `nestedVirtualization: true`, which needs an M3 or later and macOS 15. `scripts/lima/vm test linux-kvm` runs with `H9_TEST_BACKENDS=kvm,emu`.
 
## Rationale
 
**Reuse the arm64 shim and tables as they are.** KVM lets the host set every system register HVF does, through `KVM_SET_ONE_REG`. So the shim, which is only vectors and a doorbell, runs unchanged, and the shared page layout is the same. Splitting the allocator and tables out of `hvf.zig` is what makes that reuse real rather than a copy.
 
**Host-side bring-up on amd64 too.** DESIGN.md expected the amd64 shim to bring up long mode itself. KVM (`KVM_SET_SREGS`, `KVM_SET_MSRS`) and WHP (`WHvSetVirtualProcessorRegisters`) both let the host set control registers, segment state and MSRs directly, as HVF does for arm64. Doing it from the host keeps the shim to entry and exit paths, and puts the setup in Zig, where it's testable and the same for both hypervisors. The descriptor tables still live in guest memory, since the CPU reads them on every exception and `iretq`.
 
**CR3 from the shim, TTBR0 from the host.** On arm64, `KVM_SET_ONE_REG` of `TTBR0_EL1` is one cheap call, as on HVF. On x86, setting `CR3` from the host means a full `KVM_GET_SREGS` and `KVM_SET_SREGS` pair. The shared page's next-root word, which DESIGN.md's shim description already has, makes it one store and one `mov` in the shim.
 
**`KVM_SET_SIGNAL_MASK` rather than an unblocked signal.** An unblocked kick signal could land while a vCPU's thread is inside drawterm, making a host `read` fail with `EINTR` that drawterm doesn't retry. Blocking it everywhere except inside `KVM_RUN` is QEMU's approach, for the same reason.
 
**FXSAVE state, without XSAVE.** h9's FP state is the FXSAVE image ([i386](0009-i386.md) makes that `vmm.Extra`'s x86 form), which holds x87, SSE and MXCSR. Hiding XSAVE and AVX in CPUID keeps user code, Go's runtime among it, from using registers h9 wouldn't save across a vCPU switch. 9front's own 6c output uses only SSE.
 
**No vGIC or APIC.** h9 never delivers a hardware interrupt to the guest: kicks are host-side. An interrupt controller would be state to set up and tear down for nothing. arm64 KVM runs vCPUs without an in-kernel irqchip, as kvmtool and QEMU's `kernel-irqchip=off` do, and the arch timer is only wired to one when it exists.

**Recycle vCPUs inside the backend.** The alternative is to make the vmm interface say that destroyed vCPUs don't free their slots, and have the pool stop creating owned vCPUs for good once the limit is reached. That pushes one hypervisor's quirk into shared code, and gives up owned vCPUs, the fast path, for the rest of a long-running machine. A free list in `kvm.zig` keeps HVF's semantics for everything above it.
 
**A reserved real-time signal.** h9's own signals are `SIGINT`, `SIGHUP` and `SIGTERM`, and embedders may use `SIGUSR1` and `SIGUSR2`. A real-time signal is unlikely to clash, and the reservation is documented.
 
## Compatibility
 
- **`--backend auto`** on Linux uses KVM when `/dev/kvm` is usable, where it used the emulator, so `auto` runs get faster. Output and exit codes are the same: the backend tests check that every backend produces the same traces.
- **`--backend kvm`** works where it gave "not built into this h9".
- **`--check`** lists KVM on Linux.
- **`Machine.Options`:** unchanged.
- **Embedders on Linux:** `SIGRTMIN + 1` is h9's, and must stay blocked in threads that call into a machine.
- **Build:** Linux builds gain `kvm.zig` and the amd64 shim. Nothing new is linked.
- **Vendored tree:** unchanged.
## Security
 
- **What the guest reaches:** nothing new. KVM gives the same isolation HVF does: guest memory is one region of h9's own memory, and every exit comes back to h9.
- **`/dev/kvm`** gives the h9 process the right to create VMs, which is the access the backend needs and nothing more. h9 doesn't open it unless it's using KVM.
- **The shim** runs at ring 0 in the guest, with `SMEP` and `SMAP` where the CPU has them, so it can't execute or read user pages by mistake. User pages are mapped with `U/S`, and the kernel half without it, so user code can't touch the shim, the descriptor tables or the shared pages.
- **The kick signal** is blocked outside `KVM_RUN`, so it can't be used to interrupt h9 elsewhere.

## Implementation
 
1. Split `gphys.zig` and `pt_arm64.zig` out of `hvf.zig`. HVF's suite still passes.
2. `kvm_abi.zig` and `kvm.zig` for arm64: VM, memory, vCPU init, system registers, MMIO exits, FP state, kicks with the signal mask, the vCPU free list and the descriptor limit. `vmm.Kind.kvm`, `auto`, `--check` and `tools.explain`.
3. The `linux-kvm` Lima instance. The arm64 backend and `[baseline]` cases pass on it.
4. `pt_amd64.zig`, `src/arch/amd64/shim.S` and its embedding in `build.zig`, and the x86\_64 path in `kvm.zig`. The amd64 backend cases pass on an x86\_64 host. There's no local x86\_64 KVM on Apple silicon (`linux-amd64` is QEMU without acceleration), so this step is developed on a hosted x86\_64 Linux runner or a remote x86\_64 machine.
5. README (backends, `/dev/kvm` access, the Lima instance) and DESIGN.md: the Hypervisor layer's "only HVF is built" line, the `Kind` comment, the guest shims section (host-side bring-up on amd64), and the vCPU limits paragraph with KVM's measured limit. Set `status: implemented`.
## Open issues
 
- KVM's vCPU limit, measured as HVF's was, in the `linux-kvm` VM and on an x86\_64 host. Without a vGIC, arm64 KVM reports the host GIC's limit (512 with GICv3), and x86\_64 reports 1024 on recent kernels, so the reserve of 8 should stand. The measurement should also record the cost of creating and of resetting a vCPU.
- That arm64 KVM in the `linux-kvm` VM runs vCPUs with no vGIC, and offers a 36-bit IPA, as the kernel sources suggest. Both are checked by the first backend case on it.
- CI: hosted x86\_64 Linux runners expose `/dev/kvm`, though the runner user needs a udev rule to open it. Whether hosted arm64 runners do is untested. If they don't, a self-hosted M3 or later Mac, which [ci](ci.md) already needs for HVF, can run the `linux-kvm` instance.
- Landlock for paths and TCP ports plus seccomp, with `/dev/kvm` already open; the syscalls `KVM_RUN` and vCPU threads need; the Landlock ABI each target distro ships. (A research note planned for this proposal, for [host-sandbox](host-sandbox.md).) What's known from the documentation, and untested: Landlock checks a device's ioctl rights when it's opened, and vCPU fds come from an ioctl rather than a path, so creating vCPUs after the sandbox is applied isn't blocked. seccomp needs `ioctl` (filtered by request number where possible), `mmap` of vCPU fds, and `tgkill` for kicks.
- The binfmt\_misc registration on Linux, so that `./prog` runs directly, moved here from DESIGN.md's Open questions, is now [host-binfmt](host-binfmt.md): it doesn't depend on the backend.

## Updates

- 2026-11-07: Decisions and findings from the first implementation, on an x86\_64 exe.dev VM with nested KVM (Linux 6.12, Intel VT-x, API 12):
  - **FP state goes through `KVM_{GET,SET}_XSAVE`,** not `KVM_{GET,SET}_FPU`. On this kernel `KVM_GET_FPU` always reports MXCSR as 0, even after `KVM_SET_FPU` set it. The XSAVE image's first 512 bytes are FXSAVE's layout, so it maps onto `vmm.Fxsave` directly, with XSTATE\_BV set to x87 and SSE.
  - **A kick can stop the vCPU anywhere,** so `run` works out where from the PC before returning `.interrupted`. In user mode the host reads the registers into the Ureg and re-enters the shim at its restore path before the next run (on x86 that takes a get and set of the segment state, `KERNEL_GS_BASE` and the registers; on arm64 the PC and PSTATE), so a note delivered at that exit takes effect. In the shim's save path, before the doorbell, the Ureg is half written, so the host runs on to the doorbell and returns that exit instead. In the restore path the Ureg is already current. The amd64 shim puts its doorbell at a fixed offset (0x600) to make this a comparison; on arm64 the doorbell store's offset is found in the assembled shim at compile time.
  - **The kick signal is consumed after each stop** with `sigtimedwait`: KVM blocks it again before `KVM_RUN` returns, so it stays pending and would stop the next run at once. It's blocked on each vCPU thread in `createVcpu` rather than before the kernel boots, since only vCPU threads are ever sent it. Zig 0.16's `linux.sigdelset` toggles the bit rather than clearing it, so the mask is cleared by hand.
  - **The vCPU limit** on this host is 1024 (`KVM_CAP_MAX_VCPUS`, with the hard `RLIMIT_NOFILE` high enough). It's also capped by 1024 shared-page slots in the kernel half. Creating a vCPU and resetting a parked one each take well under a millisecond (see DESIGN.md).
  - **Exit cost:** nested, a bare `OUT` exit and re-entry takes about 19 µs, and a `pwrite` round trip about 28 µs (`zig build bench`), because each exit goes through both hypervisors. The 2-instruction loop runs at 5.7 G instructions/s.
  - **The amd64 shared page** holds the vCPU's GDT (at 0x800) and TSS (at 0x880) as well as the Ureg, with IST1 at the top of the page. The IDT is one page with gates for vectors 0 to 31; its limit ends there, so `INT n` from user mode is a #GP. The doorbell port is 0x99. The kernel half, the IDT and the shared pages are mapped without U/S, and table entries under PML4 entry 511 leave U/S out too.
  - **x86 also calls `KVM_SET_TSS_ADDR`** (three pages at 0xfffbd000, outside RAM), which Intel's real-mode emulation wants on some CPUs; h9 never enters real mode.
  - **Without access to `/dev/kvm`,** `auto`'s warning names the reason (`h9: warning: no access to /dev/kvm (is your user in the kvm group?); using the emulator`), from `vmm.whyUnavailable`.
  - **The pool case** lowers the descriptor limit (`ulimit -n 330`, so KVM's limit is 74 and processes own 66) rather than setting `owned_vcpus`, which the CLI doesn't expose.
  - **Untested so far:** the arm64 path (it builds for `aarch64-linux-musl`, but there's no arm64 KVM host here) and the `linux-kvm` Lima instance, which need an M3 or later Mac. The HVF refactor builds for macOS up to linking.
