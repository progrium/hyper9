# Proposal: 386 binaries

Nov 4, 2026 · Jeff Lindsay, <abbr title="AI-assisted work substantially directed by the named person, who takes responsibility for the result.">h.d.a.</abbr>

## Abstract

h9 runs 9front's 386 executables (`I_MAGIC`) as a third architecture, next to arm64 and amd64. The first backends for it are the Unicorn emulator, in 32-bit mode, and v86 in the [browser-host](0012-browser-host.md). The root tree gains `/386/bin`.

## Background

h9 knows two architectures: arm64 (`R_MAGIC`) and amd64 (`S_MAGIC`). Both are 64-bit with the 40-byte expanded a.out header, and h9's code assumes 8-byte words in a few places: syscall argument slots, the note frame, Tos, the Ureg union.

The browser host runs guest code on v86, which emulates a 32-bit x86 PC and has no long mode. 9front still builds and releases its 386 port: the January 2026 release lists a 386 ISO next to the amd64 and arm64 images. So 386 is the architecture that runs in a browser without writing a new CPU.

## Proposal

**ABI**, from `sys/src/9/pc/mem.h`, `pc/trap.c`, and `port/sysproc.c` in 9front:

| Item | 386 (`I_MAGIC`) |
| --- | --- |
| a.out header | 32 bytes: no `HDR_MAGIC`, so the entry point is the header's 32-bit `entry` |
| UTZERO (text start) | 0x1000 |
| USTKTOP (stack top) | 0xDFFFF000 (`VMAP − BY2PG`, with VMAP at 0xE0000000) |
| Stack size | 16 MiB |
| Page size, data alignment | 4 KiB, 4 KiB |
| Syscall | `INT $64`, number in AX |
| Syscall arguments | User stack from SP+4, in 8c's layout: 4-byte words, a `vlong` takes two |
| Syscall result | AX |
| Registers at entry | AX = Tos pointer (`execregs` returns it as the syscall result); SP points at argc |
| Note handler entry | No register: SP+4 = Ureg pointer, SP+8 = message, SP+0 = 0 |
| Ureg | 19 32-bit words: di, si, bp, nsp, bx, dx, cx, ax, gs, fs, es, ds, trap, ecode, pc, cs, flags, sp, ss |
| Tos | 4-byte pointers, so its layout differs from the 64-bit one |

**Changes**

- `aout.Arch` gains `i386`, and `aout.zig` parses the short header.
- `src/arch/i386.zig` provides the Ureg and the `notifyFrame`, `sanitize`, and `initExec` the other architectures have. `sanitize` keeps `cs`, `ss`, the segment registers, and the privileged flags (IOPL, IF) from the kernel's copy, as 9front's `setregisters` does.
- Syscall argument decoding takes the word size and 8c's alignment from the architecture, rather than assuming 8-byte slots. The same applies to the note frame's words and to Tos.
- `vmm.Extra` becomes a per-architecture union. arm64 keeps `{ v, fpcr, fpsr, tls }`. Both x86 architectures carry the x87 and SSE state as a 512-byte, 16-byte-aligned FXSAVE image, plus `tls`: the FS base on amd64, unused on 386. amd64 moves to this form from its XMM-only one. `initExec` sets FCW to 0x037F and MXCSR to 0x1F80 on x86. That's the one vmm interface change.
- **Unicorn** runs i386 in `UC_MODE_32` with flat segments and a hook on interrupt 64. That makes 386 testable on every host the emulator builds on.
- **Unicorn** has no single FXSAVE register, so its `getExtra` and `setExtra` assemble the image from `FPCW`, `FPSW`, `FPTAG`, `FP0`–`FP7`, `XMM*`, and `MXCSR`. One routine serves both x86 architectures, with XMM8–15 left zero on 386.
- **Root.** The pinned arm64 root ships `/386/include` and `/386/mkfile` but no `/386/bin` or `/386/lib`. `scripts/mkroot.py --arch 386` adds them by cross-compiling inside h9: after unpacking the arm64 tree, it runs `cd /sys/src && objtype=386 mk install` in a machine with the tree writable and `/sys/src` from the root (`--src`) or bound from the fetched checkout. `--arch` takes a list, so `--arch 386,amd64` also fills `/amd64`, as [go-compat](0007-go-compat.md) wants. Without `--arch` the root is arm64 only, as now. The namespace builder binds `/$cputype/bin`, and `cputype` and `objtype` come from the binary's architecture, as now.
- **Hardware backends** don't run 386: KVM, WHP, and HVF report `WrongArch` for it, as HVF does for amd64. On x86\_64 hosts the amd64 binaries are the native ones, and 386 is here for the browser host. A later backend can add a 32-bit compatibility-mode code segment and an `INT $64` gate to its shim without touching `src/arch/i386.zig`, which stays backend-independent.

## Rationale

**Cross-compiling the 386 userland, not extracting it from the 386 ISO.**
- **One revision:** the binaries are built from `NINEFRONT_REV`, the source the arm64 tree came from, so the two architectures can't drift apart. Nothing new is pinned in `scripts/pins.sh`.
- **No second image:** extracting `/386` means downloading the 386 ISO, hundreds of megabytes, and reading it with an ISO 9660 reader or booting it in `qemu-system-i386`.
- **It's shown to work:** [self-host](0010-self-host.md) runs `cd /sys/src && mk install` in about a minute, with output byte-identical to the shipped binaries, and builds `objtype=amd64` libraries and commands the same way.
- **The cost:** the binaries are built by the code under test, so a bug in h9 could produce bad binaries. A one-time comparison against the release ISO's `/386/bin` checks that; only binaries with embedded build dates should differ, as on arm64. Building also needs h9 itself and `/sys/src`, which is why `--arch` is opt-in.

**Leaving 386 to emulation on KVM.** No user needs 386 on an x86\_64 host, where amd64 binaries run natively, and SPEC.md runs native binaries only. [KVM](0016-kvm.md)'s long-mode shim isn't built yet, and compatibility mode would add a 32-bit code segment, a user-callable gate for vector 64, and a 32-bit Ureg path to it. Keeping `src/arch/i386.zig` free of backend details leaves that open.

**FXSAVE for amd64 too, not only 386.**
- **Completeness:** the image holds XMM0–15 and MXCSR, which amd64's form already has, plus the x87 control, status, tag, and stack registers, which it drops today. 9front saves the whole area for every process.
- **Backends:** KVM (`KVM_GET_FPU`, `KVM_GET_XSAVE`), WHP, and v86 all deal in this layout, so they copy it rather than convert it.
- **One x86 path:** Unicorn's conversion is written once for both architectures, and is the only backend that has to assemble the image.
- **The cost:** 512 bytes copied per context switch instead of about 260, which doesn't show next to a vCPU exit.

## Done when

- The `[baseline]` cases pass with `--backend emu` on a root with `/386/bin`, on macOS arm64 and Linux x86\_64.
- `tests/backends.zig` has i386 versions of hello, exits, faults, kicks, notes, and the vCPU pool carrying FP state, and the amd64 FP case checks x87 state across a vCPU switch.
- `scripts/mkroot.py --arch 386` produces a root whose `/386/bin` matches the 386 ISO's, except for binaries with embedded build dates.

## Updates

- 2026-11-05: Refinements made while implementing it:
  - **`--arch arm64|amd64|386`** picks the architecture of the binaries a machine runs. Without it a host program (`./x`) runs as its header says and a guest one as the host's, as before; nothing else could run `/386/bin` from the root, which the `[baseline]` criterion needs. The integration cases pass it from `-Darch` (`H9_TEST_ARCH`), on the emulator only when it isn't arm64. `mkroot.py --arch` runs its build with `--arch arm64`, so the arm64 compilers run on any host.
  - Unicorn's `getExtra` and `setExtra` use its `ST0`–`ST7` registers, which are in stack order as FXSAVE stores them, rather than `FP0`–`FP7`, which are physical registers and would need rotating by TOP. The status word, which holds TOP, is written before them.
  - `aout.header_size` stays the largest header (40 bytes); `Arch.headerSize()` gives each one's, and the symbol table's values are 4 bytes on 386.
  - The vmm module names the ABI `ia32`, since `i386` is a Zig primitive type; the file is `src/arch/i386.zig` and the `Arch` tag is `.i386`, whose 9front name (`cputype`, `/$cputype/bin`) is `386`.
- 2026-11-07: `scripts/mkroot.py` is now a Zig tool, `tools/mkroot.zig`, run as `zig build mkroot -- --arch 386,amd64`, so building the root needs no Python. Without `--arch` it now builds the host's architecture (amd64 on x86\_64, 386 on x86), rather than leaving the root arm64 only; `--arch arm64` gives the arm64-only root.
