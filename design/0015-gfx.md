# Proposal: graphics (--gfx)

Nov 5, 2026 · Jeff Lindsay, <abbr title="AI-assisted work substantially directed by the named person, who takes responsibility for the result.">h.d.a.</abbr>

## Abstract

`--gfx` gives a machine one host window, drawn by drawterm's own GUI backends (Cocoa on macOS, Win32 on Windows, X11 on Linux), and serves `/dev/draw`, `/dev/mouse`, `/dev/cursor`, and `/dev/kbd` from it, with `/dev/snarf` mapped to the host clipboard. rio and acme run in it. The console stays the host terminal. Without `--gfx`, the draw, mouse, and keyboard devices are masked, so a guest can't open a window.

## Background

This was milestone M7 in DESIGN.md, before milestones became proposals ([#1](0001-proposals.md)). The design text there was:

> **Graphics (`--gfx`):** opens one host window through drawterm's GUI backend (Cocoa/Metal, X11 or Wayland, Win32) and serves `/dev/draw`, `/dev/mouse`, and `/dev/kbd`, plus snarf mapped to the host clipboard. One screen per machine: running rio gives the full desktop. A seamless mode, where each rio window becomes a host window, is a later project.

### h9 today

- **The devices are built.** devdraw (`#i`), devmouse (`#m`) and devkbd (`#b`) are compiled from drawterm and listed in `src/kern/devtab.c`. They aren't bound anywhere, and they aren't in the device mask.
- **There's no screen.** `src/kern/glue.c` stubs drawterm's screen interface: `attachscreen` returns nil, so an attach of `#i` fails with "no frame buffer"; `clipread` returns nil and `clipwrite` drops the text, so `/dev/snarf` (served by drawterm's devcons, which is bound at `/dev`) is a dead end.
- **The GUI backends aren't built.** `third_party/drawterm` has `gui-cocoa`, `gui-x11`, `gui-wl`, `gui-win32`, and others, and `build.zig` leaves them all out.
- **The console** is `#y`, h9's per-machine console device, on the host TTY. drawterm's own `#c/cons` isn't used for input.

### How drawterm's GUI backends work

Each backend implements one interface (`kern/screen.h`): `screeninit`, `attachscreen`, `flushmemscreen`, `setcursor`, `mouseset`, `getcolor`/`setcolor`, `clipread`/`clipwrite`, and `guimain`. It feeds input back with `absmousetrack` (into devmouse) and `kbdkey` (into devkbd). There's one screen per host process: `gscreen`, the mouse state, and devdraw's client tables are globals.

- **When the window opens.** devdraw's attach calls `screeninit` the first time, if `gscreen` is still nil. On X11 and Win32, `screeninit` opens the window and starts a kproc for the event loop (`xproc`, `winproc`).
- **Cocoa is different.** AppKit must run on the process's main thread, so drawterm's `main` calls `guimain`, which runs `[NSApp run]` there and never returns. The app delegate then creates the window, starts a kproc that calls `cpubody` (the rest of drawterm), and waits in `ksleep` until a client attaches `#i` and `screeninit` runs. That `ksleep` means drawterm's main thread is a kernel Proc.
- **Keys.** `kbdkey` queues a key on `/dev/kbd` while it's open, in the `r`/`R` rune format rio reads. Otherwise it puts the rune on drawterm's console queue, `kbdq`, which only drawterm's `#c/cons` reads.
- **Closing the window** calls `exit(0)` on X11, `ExitProcess(0)` on Win32, and on Cocoa ends the app, which calls `exit` from AppKit.
- **Linking.** Cocoa needs the Cocoa, Metal, and QuartzCore frameworks, Win32 needs `gdi32` and `user32`, X11 needs `libX11`, and Wayland needs `libwayland-client`, `libxkbcommon`, and `libdecor`. h9's Linux builds are static musl, which can't load any of the Linux ones.

rio posts its file server to `/srv` and its windows mount it, hence [devsrv](0008-devsrv.md).

## Proposal

### The flag and the library

| Flag | Meaning |
| --- | --- |
| `--gfx` | Gives the machine a host window and serves `/dev/draw`, `/dev/mouse`, `/dev/cursor`, and `/dev/kbd` from it, and the host clipboard as `/dev/snarf` |
| `--gfx=noclip` | The same, but `/dev/snarf` is a buffer in the h9 process, not the host clipboard |
| `--gfx-scale=N` | Screen scale, drawterm's `-x N`: 0 is backing pixels, 1 points, N backing pixels divided by N. Default 1. Cocoa only for now; other backends ignore it |

`Machine.Options` gains `gfx: ?Gfx = null`, where `Gfx` is `struct { clipboard: bool = true, scale: u8 = 1 }`. The screen belongs to the host process, so at most one machine in a process can have it at a time. `Machine.init` fails with:

- `GfxNotBuilt` when this h9 has no GUI backend (see Build). The CLI prints "graphics aren't built into this h9" and exits 125.
- `GfxInUse` when another machine in the process has the screen.
- `GfxUnavailable` when there's no display: `$DISPLAY` unset on X11, or, on macOS, the calling program didn't hand its main thread to `h9.gfx.main` (below). Exit 125, with the reason.

**The main thread.** A new `src/gfx.zig`, exported from `src/root.zig`:

```zig
/// Runs `work` with the GUI set up. On macOS this must be called on the
/// process's main thread: it gives that thread to AppKit and runs `work`
/// on a new thread, and returns only through `work`'s exit code. Elsewhere
/// it calls `work` directly.
pub fn main(work: *const fn (?*anyopaque) u8, ctx: ?*anyopaque) noreturn;
```

`src/main.zig` calls it when `--gfx` is given, so the CLI's flow is otherwise unchanged. An embedder that wants a window does the same. On macOS, `main`:

1. Boots the kernel, on its private thread as now.
2. Makes the main thread a kernel Proc with a new `h9_kern_adopt` in `src/kern/proc.c`, which clones from the boot Proc as `h9_kern_spawn` does, but for the calling thread. Cocoa's delegate needs `up` for its `ksleep`.
3. Starts `work` on a new thread.
4. Calls drawterm's `guimain`, which runs AppKit.

drawterm's backends end their setup by calling `cpubody`. h9 defines it, in `src/kern/gfx.c`, to mark the screen ready and return. On macOS `work`'s machine run waits for that before it starts, so the first attach of `#i` finds the window.

### Devices and the namespace

With `--gfx`, the namespace builder appends the three devices to `/dev` after `#c` and `#y`:

```text
  bind -a '#i' /dev
  bind -a '#m' /dev
  bind -a '#b' /dev
```

That gives `/dev/draw/`, `/dev/mouse`, `/dev/cursor`, `/dev/mousectl`, and `/dev/kbd`, the files rio and libdraw open. `/dev/snarf` is already there from `#c`, and its `clipread` and `clipwrite` now reach the host clipboard through the backend. With `--gfx=noclip`, `src/kern/gfx.c` answers them from an in-process buffer instead, the headless backend's code, so snarf still works between the guest's programs but never reaches the host.

Without `--gfx`, `#i`, `#m`, and `#b` join the device mask, so a guest can neither attach the devices to open a window nor read another machine's.

**When the window opens:** at the first attach of `#i`, as in drawterm, except on macOS, where AppKit opens it at start. A program that never draws (`h9 --gfx ls`) opens no window on X11 or Windows.

**The console** stays the host terminal: `/dev/cons` is `#y`, as without `--gfx`. Window keys go to `/dev/kbd` while a program has it open, which rio does. While nothing has it open, `kbdkey` puts them on drawterm's `kbdq`, which nothing in h9 reads, and they're dropped once it's full: `kbdq` is non-blocking, so the backend's event thread never stalls on it. So programs that draw and read the keyboard through `/dev/cons`, such as acme or sam started on their own, run inside rio: `h9 --gfx rio -i 'window acme'`.

**Screen scale and geometry:** the backends read two globals from drawterm's `cpu.c`, which h9 doesn't build, so `src/kern/gfx.c` defines them. `geometry`, X11's window geometry string (drawterm's `-g`), is nil, so the window takes the backend's default size. `scalef` is read only by Cocoa: 0 draws in the display's backing pixels, which on a Retina display makes text half the size of other Mac apps, 1 draws in points, and N in backing pixels divided by N. h9 sets it from `--gfx-scale`, and its default is 1 on macOS, so the window looks like any other Mac app's. X11 and Win32 ignore it and draw in device pixels.

### Closing the window

Closing the window does what closing the terminal does: it posts `hangup` to every process, waits up to the 2 s grace period, then tears the machine down, and h9 exits with the run's status.

- **X11 and Win32.** The backend files are compiled with `-Dexit=h9_gfx_exit` and `-DExitProcess=h9_gfx_exit`, as `devpipe.c` is compiled with `-Dpostnote=h9_postnote` today. `h9_gfx_exit` calls the machine's `Signals.hangup` and parks its thread. The vendored tree stays unmodified.
- **Cocoa.** AppKit calls `exit` itself, so h9 observes `NSApplicationWillTerminateNotification` from its own `src/kern/gfx-cocoa.m`. The observer calls `Signals.hangup`, waits for the run to end or the grace period to pass, and calls `_exit` with the run's exit code. That's the Windows console close handler's pattern, and it covers the close button and Quit.
- **The other way round:** when the run ends, h9 exits, which closes the window.

### Build

`-Dgfx=cocoa|win32|x11|headless|none` picks the backend:

| Host | Default | Notes |
| --- | --- | --- |
| macOS | `cocoa` | `gui-cocoa/screen.m`, compiled by `zig cc` as Objective-C with the macOS SDK (`SDKROOT`, from `scripts/env.sh`), linking Cocoa, Metal, and QuartzCore. Built on a Mac, like h9's HVF build already is |
| Windows | `win32` | `gui-win32/screen.c`, linking `gdi32` and `user32` from Zig's MinGW |
| Linux | `none` | `x11` builds `gui-x11/x11.c` and `keysym2ucs-x11.c` against a glibc target (`-Dtarget=x86_64-linux-gnu`), linking the system's `libX11` |
| any | | `headless` is for tests, below |

The no-op stubs in `src/kern/glue.c` move to `src/kern/nogfx.c`, built with `none`. `--version` lists the GUI backend, and `--check` reports it, and on X11 whether `$DISPLAY` can be opened, without opening a window.

**The headless backend,** `src/kern/gfx-headless.c`, is a screen in memory: `screeninit` allocates `gscreen` at a fixed size, `flushmemscreen` does nothing, and the clipboard is a buffer. `src/gfx.zig` exposes it to tests: inject a key or a mouse event, read the clipboard, copy the screen's pixels, and close the window. It's built for `zig build test`, so the cases below run on every host and in CI without a display.

### The plan

`--print` gains a `gfx:` line naming the backend, the scale, and whether the clipboard is shared when `--gfx` is given, and the device mask shows `#b #i #m` when it isn't. Caveats with `--gfx`:

- "the guest can read and write the host clipboard through /dev/snarf" (not with `noclip`)
- "the guest can draw anything in its window, including what looks like a host dialog"

## Rationale

**drawterm's backends, not new ones.** They're what drawterm ships to 9front users on these hosts, they speak devdraw's screen interface already, and they're vendored. Writing h9's own would mean three window systems' worth of input, cursor, and clipboard code for no gain.

**The console stays the terminal.** h9 is run from a terminal, and that's where stdout, stderr, `--trace`, and exit messages belong. 9front's own model is rio: it reads `/dev/kbd` and serves each window its own `/dev/cons`. Making the window the console would need a cooked line discipline, echo, and a text console drawn on the screen (drawterm's `term.c`) that rio would then draw over. Programs that want the window's keyboard on `/dev/cons` run in rio, which is the 9front way to run them. A window console mode (`--gfx=console`, say, drawing drawterm's `term.c` and feeding `kbdq` to `#y`) can come later, in its own proposal, without changing this one.

**One screen per host process, and an error for a second.** `gscreen`, devmouse's state, and devdraw's tables are globals in drawterm, and making them per machine would change most of devdraw. The CLI runs one machine anyway. Masking `#i`, `#m`, and `#b` for every other machine keeps the one screen from leaking across machines.

**Masking the devices without `--gfx`.** Once a backend is built in, an unmasked `#i` would let any guest open a host window and read the host clipboard. The mask makes the window an explicit grant, like `#C` with `--host-cmd`.

**Adopting the main thread on macOS, rather than booting the kernel there.** The boot thread parks for good after boot (`h9_kern_park`), and the main thread has to run AppKit. Adoption is `h9_kern_spawn`'s cloning without the new thread, so the kernel keeps one boot path.

**The clipboard on by default, with `noclip` to turn it off.** Sharing snarf with the host is most of what makes rio and acme usable next to host apps, and the window is already an explicit grant. Runs that want a window without that channel say `--gfx=noclip`; the buffer keeps snarf working inside the guest.

**Points by default on macOS.** Backing pixels, drawterm's default, make every Retina Mac's text tiny. Points match other Mac apps, and `--gfx-scale=0` gets native pixels back. X11 and Win32 HiDPI handling would need backend changes, so the flag is Cocoa-only for now.

**Redirecting `exit` with macros, not editing the backends.** It's the pattern `build.zig` already uses for `postnote`, keeps the vendored tree unmodified, and lets a closed window go through the same hangup path as a closed terminal.

**X11 first on Linux, not Wayland.** drawterm's Linux default is now Wayland, but its backend needs three libraries to X11's one, and X11 programs run on Wayland desktops through XWayland. Either needs glibc and dynamic linking, which is why Linux gfx is a build option rather than the default, and Linux releases stay the static `h9` until there's demand for a separate gfx build. A Wayland backend gets its own proposal if XWayland proves inadequate.

**A headless backend for tests.** A window system can't be relied on in CI or the Lima VMs. A memory screen tests everything above the backend (devdraw, the namespace, rio, input, and the clipboard paths), and only the backends' own window code is left to the demos.

**Not in this proposal:** a seamless mode, where each rio window is a host window. That's a rio replacement, or a devdraw that knows windows, and a project of its own.

## Compatibility

- **CLI:** `--gfx`, `--gfx=noclip`, and `--gfx-scale` are new. Exit 125 when it can't be honoured, as for a missing hypervisor.
- **`Machine.Options`:** `gfx` is new, with the errors above, and `h9.gfx.main` is new.
- **Sandbox defaults:** `#b`, `#i`, and `#m` are masked in every machine without `--gfx`. Nothing could use them before, since there was no screen.
- **Seam rules:** rule 4 (DESIGN.md) gains an exception: on macOS with `--gfx`, the main thread is adopted as a kernel Proc, through drawterm's own clone path.
- **Build and releases:** macOS and Windows builds gain the GUI backend by default, and with it framework and system-library links. Linux builds and releases are unchanged unless `-Dgfx=x11` is given.
- **Vendored tree:** unchanged. The GUI files are compiled as they are, with macro redirections, and `cpubody`, `scalef`, and `geometry` are defined by h9.

## Security

- **What the guest newly reaches,** only with `--gfx`: one window it draws in, the keyboard, and mouse while that window has focus, and the host clipboard. Focus means a guest can't read keys typed into other host windows.
- **The clipboard** is a two-way channel to the host. Reading it can expose whatever the user last copied, such as a password. The plan lists it as a caveat, and `--gfx=noclip` closes it.
- **Without `--gfx`,** the devices are masked, so a guest gets none of this, even in a build with a backend.
- **Between machines,** only the machine with the screen has the devices unmasked.
- **The window system** is reached through the backend's own library calls in the h9 process, not by the guest: devdraw draws into memory, and the backend copies it to the window.

## Done when

Backend cases in `tests/backends.zig`, on the headless backend, tagged `[gfx]`:

- `test "--gfx binds /dev/draw, /dev/mouse, /dev/cursor and /dev/kbd [gfx]"`
- `test "reading /dev/draw/new reports the screen's size [gfx]"`
- `test "a draw client's image reaches the screen [gfx]"`: the captured pixels change from the background.
- `test "a key injected into the window reaches /dev/kbd [gfx]"`
- `test "a mouse event injected into the window reaches /dev/mouse [gfx]"`
- `test "/dev/snarf reads and writes the host clipboard [gfx]"`
- `test "with --gfx=noclip, /dev/snarf keeps its text but leaves the host clipboard alone [gfx]"`
- `test "rio starts, and a window's rc runs a command typed into it [gfx]"`: `rio -i 'window rc'`, then typed keys run `echo hi > /dev/snarf`, and the clipboard reads `hi`.
- `test "acme starts inside rio [gfx]"`
- `test "closing the window posts hangup and ends the run [gfx]"`
- `test "a second machine in the process gets GfxInUse [gfx]"`

Integration cases, on any build:

- `test "without --gfx, #i, #m and #b are masked [gfx]"`
- `test "--gfx on a build without graphics exits 125 [gfx]"`, in a `-Dgfx=none` build.

Demos, by hand, one per backend: `h9 --gfx rio` opens a window with rio on macOS, Windows, and Linux (X11), and `h9 --gfx rio -i 'window acme'` runs acme in it, with snarf reaching the host clipboard and closing the window ending h9.

## Implementation

1. `src/kern/nogfx.c` (the stubs, moved), `-Dgfx`, and the masking of `#b`, `#i`, and `#m` without `--gfx`. The masking case passes.
2. `src/kern/gfx-headless.c` and `src/gfx.zig`'s test hooks, `Machine.Options.gfx`, the `/dev` binds, `GfxInUse`, and `cpubody`, `scalef`, `geometry`, and the `noclip` buffer in `src/kern/gfx.c`. The headless cases that don't need rio pass.
3. `--gfx`, `--gfx=noclip`, and `--gfx-scale` in `src/cli.zig`, the plan's `gfx:` line and caveats, `--version`, and `--check`.
4. X11: `-Dgfx=x11`, `h9_gfx_exit`. The X11 demo works.
5. Win32: `-Dgfx=win32` as the Windows default. The Windows demo works.
6. Cocoa: `h9_kern_adopt`, `h9.gfx.main`, and `gfx-cocoa.m`. The macOS demo works.
7. With [devsrv](0008-devsrv.md) implemented, the rio and acme cases.
8. README: `--gfx` and the build option. DESIGN.md: the Decisions table's Terminal row, the boot sequence's binds and device mask, the CLI flag table, seam rule 4's exception, and the Seatbelt research note if [host-sandbox](host-sandbox.md) hasn't taken it. Set `status: implemented`.

Running `h9 --gfx rio` under a `(deny default)` profile with `(trace ...)` during step 6 would answer it; likely candidates are `com.apple.windowserver.active`, `com.apple.CARenderServer`, `com.apple.pasteboard.1`, and Metal's IOKit classes.

## Updates

- 2026-11-07: Refinements made while implementing it:
  - The window opens lazily through a wrapper around devdraw's devtab (`h9drawdevtab` in `src/kern/gfx.c`), not in the bind: attaching and listing `#i` don't open the screen, and the first walk into it does. rio opens `/dev/snarf` before the display, so opening `/dev/snarf` also opens the screen; a process with `#i` masked can't open `/dev/snarf` at all.
  - `/dev/kbd` serves kbdfs's format (`k`/`K` with the keys held, `c` for each key typed, with Ctrl applied), which rio and kbdfs's clients read, instead of drawterm's `r`/`R`. Keys typed while it isn't open are dropped rather than queued on the console's input queue, which would have echoed them to the host terminal.
  - The backend's exits are redirected by `src/kern/gfx-gui.h`, force-included before the backend's source, with function-like macros rather than `-D` flags, because a `-DExitProcess=...` would also rename Windows' own `dllimport` declaration. The same header renames `screeninit`, `clipread`, `clipwrite`, and `kbdkey` to h9's wrappers. On Win32 `FreeConsole` becomes a no-op, since the console is still the guest's.
  - The backend's kprocs (its event loop) run in a fresh, empty namespace and fd group of their own (`h9_kern_isolated`), so they don't share the guest's.
  - `screenputs` is cleared after the screen opens, so kernel prints stay on the host terminal rather than on the window.
  - rio writes `rawon` to `/dev/consctl`, which is still the host terminal's (`#y`), so the host terminal is in raw mode while rio runs.
  - Closing the window parks the backend's thread after posting `hangup`, rather than returning, since the vendored code expects `exit` not to return.
  - On macOS `acquire` waits up to 10 s for AppKit to open the window, then fails with `GfxUnavailable`.
  - The test module (`zig build test` and `install-tests`) is always built with the headless backend, whatever `-Dgfx` is, so the `[gfx]` backend cases run on every host.
  - rio needs `/mnt/temp` in the root tree; `scripts/mkroot.py` now makes it, and adds the mount points to a tree it built before.
  - The X11 backend's `x11.c` includes `<X11/IntrinsicP.h>`, so `-Dgfx=x11` needs the libXt headers as well as libX11, and builds natively against glibc only; the emulator's prebuilt Unicorn is musl-only, so an X11 build with the emulator needs `-Dunicorn=source`.
  - [host-sandbox](host-sandbox.md) already lists the Seatbelt question, so DESIGN.md gets no research note.
