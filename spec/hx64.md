# hx64: h9's amd64 CPU

This describes hx64 as built. hx64 is h86 in long mode: the same encoding table, decoder, interpreter (T0), and lifter (T1) under `src/interp/x86/` and `src/jit/x86/`, instantiated with a comptime `Mode` of `.long` instead of `.legacy`. It runs 9front's and Linux's amd64 programs on the emulator backend, natively and on the web host. [h86](h86.md) describes everything the two modes share, and this spec covers only what long mode adds. What every CPU shares (the emulator backend, the TLB, the IR, the emitters, and the code cache) is in [jit.md](jit.md), and why hx64 exists is in the [174](../design/hcpu.md) proposal.

## Scope

- **A ring-3, flat, 64-bit long-mode process.** There are no segments apart from the FS and GS bases, and no kernel mode, paging, descriptor tables, or devices.
- **Instructions:** h86's integer, string, x87, MMX, SSE, and SSE2 instructions at every operand size long mode has, with REX, plus `MOVSXD`, `MOV` with a 64-bit immediate and `moffs64`, `CMPXCHG16B`, `LAHF` and `SAHF`, and `SYSCALL`, which is x86-64-v1, and SSE3, SSSE3, SSE4.1, SSE4.2 (with `CRC32`), and `POPCNT`, which make it x86-64-v2. h86 has none of v2.
- **Everything else faults.** The opcodes long mode removes (`PUSHA`, `POPA`, the BCD ops, `BOUND`, `LDS`, `LES`, `INTO`, and the one-byte segment pushes and pops) raise #UD. `INT n` raises #GP, `INT3` is a breakpoint, and privileged instructions raise #GP as on h86.

**CPUID** reports h86's "GenuineIntel", family 6, and leaf 1 with SSE3, SSSE3, CMPXCHG16B, SSE4.1, SSE4.2, and POPCNT added, plus long mode, `SYSCALL`, NX, and `LAHF`/`SAHF` in the extended leaves. Nothing in v3 or past it is reported (AVX, OSXSAVE, BMI, `LZCNT`, and `MOVBE`), nor AES or PCLMULQDQ, so `F3 0F BC` and `BD` run as `BSF` and `BSR`. The brand string is "hx64 amd64 interpreter". The Linux personality's `/proc/cpuinfo` lists the same v2 flags for amd64 on every backend.

## State

`src/interp/x86/cpu.zig`'s `Cpu64`:

| Field | What |
| --- | --- |
| `r` | RAX to R15, in encoding order, as u64 |
| `rip` | |
| `fl` | RFLAGS: the materialized bits and the lazy record, whose operands are 64 bits for both modes ([jit.md](jit.md), The IR) |
| `fs_base`, `gs_base` | Set by `arch_prctl` and 9front's TLS |
| `fpu`, `xmm`, `mxcsr` | h86's x87, sixteen XMM registers, and MXCSR |
| `trap`, `ecode` | Ureg.type and the error code, as the last exit left them |
| `icache`, `pages` | Long mode's decode caches, which the Guest allocates |
| `retired` | Guest instructions retired |

A 32-bit write zeroes the upper half of its register, as the hardware does. `getUreg` and `setUreg` convert to and from 9front's amd64 Ureg, and `getExtra` and `setExtra` copy the FXSAVE64 image, with 64-bit FIP and FDP.

## Exits

| Exit | When | Ureg.type | RIP |
| --- | --- | --- | --- |
| `.syscall` | `SYSCALL`, for 9front and Linux both | 64 | Past it, with the return RIP in RCX and RFLAGS in R11, as the hardware leaves them |
| `.breakpoint` | `INT3` | 3 | Past it |
| `.fault`, with the address and access | A page fault | 14 | At the instruction |
| `.fault`, with the vector | #DE, #UD, #GP, #MF, or #XM | The vector | At the instruction |

Every exception is precise, as on h86.

## Decoding

`decodeIn(.long)` reads legacy prefixes, then REX, whose W bit gives a 64-bit operand size over `66`. The three-byte maps, `0F 38` and `0F 3A`, are a table row each (all take ModRM, and `0F 3A` an imm8), with the third byte in `Inst64.op3`; like `POPCNT` (`F3 0F B8`) and SSE3's `0F 7C` and `7D`, they're in the long-only rows, so they're #UD in legacy mode. Its R, X, and B bits extend ModRM's fields to sixteen registers. Byte registers 4 to 7 name SPL, BPL, SIL, and DIL whenever a REX is present. Operations that default to 64 bits (`PUSH`, `POP`, near `CALL`, `RET`, and `JMP`, and `Jcc`) are marked `d64` in the table, and the ones long mode removes are marked `inv64`. ModRM with mod 0 and r/m 5 is RIP-relative, and `67` selects 32-bit addressing. `effectsIn(.long)` gives each instruction's read and write sets over sixteen registers, for the lifter.

## T0

`exec.ExecIn(.long, M)` is h86's interpreter, generic over the mode, with the 386's `Exec(M)` unchanged. In long mode, shifts and rotates mask their counts to 6 bits at 64-bit size. `MUL`, `IMUL`, `DIV`, and `IDIV` work at 128 bits. String ops and `LOOP` and `JRCXZ` use RCX, RSI, and RDI, or ECX, ESI, and EDI under `67`, zero-extending as the hardware does. x87 and SSE go to `x87.zig` and `sse.zig`, which take the long-mode `Exec` for REX, XMM8 to XMM15, and RIP-relative operands. `sse.zig` hands x86-64-v2's vector instructions to `sse4.zig`: the `0F 38` and `0F 3A` maps by `op3`, and SSE3's forms in the `0F` map, which it asks about first. SSSE3's integer instructions have MMX forms, as SSE2's do. `DPPS` and `DPPD` sum their products in a different order for each lane, as Intel's CPUs do, which shows in which NaN a lane gets. `POPCNT` is in `exec.zig`.

## T1

`lift.zig`'s `LifterOf(.long)` lifts:

- control flow, the integer ALU, and flags at 64 bits
- shifts, rotates, MUL, and DIV below 128 bits
- moves, `MOVSXD`, `LEA`, the stack, `CMOVcc`, `SETcc`, `BT`, and `SHLD`
- strings and `REP`
- `LOCK` atomics, through `cas`
- SSE and SSE2, with XMM8 to XMM15 and the 64-bit forms under REX.W
- `POPCNT`, as the IR's `popcnt` (a bit-slicing count on x86-64 hosts, which needn't have `POPCNT`)

128-bit `DIV`, `CMPXCHG8B` and `CMPXCHG16B`, x87, and SSE3, SSSE3, SSE4.1, and SSE4.2 run through `call.interp` (`lift.interpLong`). Every region is marked `tso`. On arm64 hosts, 64-bit `eflags.*` producers set the host's NZCV, so conditions on them are host branches.

T1 is the default on x86-64 and arm64 hosts and on the web host, where `runWasmT1` compiles hot blocks to wasm as h86's does. `H9_EMU_TIER` picks a tier.

## Testing

- **T0 against the host CPU:** `zig build x64check -- n seed int|x87|sse|v2` runs random instructions natively in long mode (`tools/x86check/oracle64.c`) and on T0. `v2` draws x86-64-v2's forms (SSE3, SSSE3, SSE4.1, SSE4.2, `CRC32`, and `POPCNT`) with their mandatory prefixes. This needs an x86-64 Linux host whose CPU has v2.
- **Lockstep:** `zig build fuzz-x64` runs random long-mode programs (`gen_x86.program64`) against the oracle ([jit.md](jit.md#testing)). The oracle's own long-mode errors (non-canonical accesses, `SHLD`/`SHRD` with a RIP-relative imm8, and 32-bit `CMPXCHG`) are known divergences.
- **The region check:** `check.x86.guest64` checks lifted regions against T0, and `zig build fuzz-long` includes `fuzz-x64`.
- **Litmus:** `zig build litmus` runs long mode's store buffering, message passing, `XADD`, and `CMPXCHG16B` counters on every tier.
- **`zig build x64-jit`** runs the `[hcpu]` cases in `tests/x64.zig` on T0, on T1 in `ir_eval`, and on T1 natively.
- **`zig build x64-inventory`** reports the instructions in amd64 binaries, for choosing what to lift next.
- **Integration:** `zig build integration -Darch=amd64` runs the suite with an amd64 root (the 9front ISO through `zig build isoroot`, and Alpine), with `-Djit-check` checking every region.
