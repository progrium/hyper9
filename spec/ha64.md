# ha64: h9's arm64 CPU

This describes ha64 as built on the `vcpu` branch. ha64 is a user-mode arm64 CPU in Zig that runs 9front's and Linux's arm64 programs on the emulator backend in a `-Demu=zig` build, in place of Unicorn. Its design follows rv64.js and v86: an interpreter that is the first tier and the oracle, and a region JIT through a small IR. What it shares with h86 (the emulator backend, the TLB, the IR, the emitters, and the code cache) is in [jit.md](jit.md); why it exists is in the [hcpu](../design/hcpu.md) proposal.

## Scope

- **All of Armv8.0's A64 instructions at EL0:** integer, branches, loads and stores, exclusives, load-acquire and store-release, FP, and Advanced SIMD, including the SIMD structure loads and stores. That's what Linux programs may use without asking, and what h9's `AT_HWCAP` has always advertised.
- **Optional extensions,** each advertised on the emulator through `vmm.Backend.hwcaps` because both tiers run it: the Armv8.1 LSE atomics (`HWCAP_ATOMICS`), CRC32, AES with PMULL, SHA1, and SHA256 (`src/interp/a64/ext.zig`). Hardware backends and Unicorn's advertise none, and programs find what the CPU has by trying.
- **Nothing of a system:** no EL1, MMU, exceptions taken to a guest kernel, interrupts, devices, AArch32, SVE, or SME. Later architecture versions' encodings (FP16 arithmetic, RDM, and the dot product) decode as undefined.

## State

`src/interp/a64/exec.zig`'s `Cpu`:

| Field | What |
| --- | --- |
| `r` | Register slots: X0 to X30 in 0 to 30, reads of ZR from slot 31 (always 0), writes to ZR into slot 32 (a sink), and SP in 33. The decoder resolves which an encoding means, so no handler tests for register 31. |
| `pc` | |
| `nzcv` | N, Z, C, and V in bits 31 to 28, as PSTATE and the NZCV register have them |
| `fpcr`, `fpsr` | FPCR's AHP, DN, FZ, and RMode (the trap enables read as zero and ignore writes, as on Apple cores); FPSR's QC and cumulative flags |
| `v` | V0 to V31, 128 bits each |
| `tpidr`, `tpidrro` | TPIDR\_EL0 and TPIDRRO\_EL0 |
| `monitor` | The exclusive monitor: the address, size, and value of the last load-exclusive |
| `retired` | Guest instructions retired |

`getUreg` and `setUreg` copy X0 to X30, SP, PC, NZCV (as `psr`), and the last exit's ESR (as `type`) to and from 9front's arm64 Ureg; `setUreg` also clears the exclusive monitor, since a context switch does. `getExtra` and `setExtra` copy the V registers, FPCR, FPSR (masked to the bits Armv8.0 has), and TPIDR\_EL0.

## Exits

Every exit carries the ESR the hardware would report to EL1, which becomes Ureg.type and the fault's syndrome, so the kernel and the Linux personality see what they see on HVF:

| Exit | EC | PC |
| --- | --- | --- |
| `.syscall` (SVC) | `0x15` | Past it |
| `.breakpoint` (BRK) | `0x3c` | At it |
| `.fault`: a data abort | `0x24`, with a translation, permission, or alignment fault status | At the instruction |
| `.fault`: an instruction abort | `0x20` | At the instruction |
| `.fault`: a misaligned PC | `0x22` | At the branch's target |
| `.fault`: an undefined instruction | `0` | At the instruction |

An EL0 `MRS` of a register T0 doesn't serve, such as an ID register, is undefined, so the Linux layer's `emulateIdRead` sees the same fault it sees on HVF.

## Decoding

`src/interp/a64/decode.zig` turns an instruction word into a micro-op (`Op`): a kind and operand fields (`d`, `n`, `m`, `a`, `x`, `sh`, and `imm`), with immediates expanded and branch targets already resolved against the PC. `regs` gives each micro-op's register read and write sets, which the lifter's flag liveness and the verbatim copier use. T0, the lifter, and the inventory tool (`tools/a64inv.zig`) share it.

The integer, branch, system, and load and store classes are in `decode.zig`, including loads and stores of single FP and SIMD registers. FP and AdvSIMD data processing and the SIMD structure loads and stores are in `simd_decode.zig`, whose kinds start at `simd_base`, and the extensions' encodings in `ext.zig`, from `ext_base`. Anything none of them implements decodes to `.undef`.

## T0

`src/interp/a64/exec.zig` decodes each executable page once, on its first fetch, into 1024 micro-ops and a sentinel (`Cache`), and runs them. Each kind has its own small handler, found through a table, so no one function holds the instruction set: wasm engines reject a function with that many locals, and optimizing one takes minutes. A page's decoded ops hold until `CodePages` invalidates it.

Guest memory goes through the vCPU's TLB, the same one generated code checks inline, and `mem.probe` on a miss. The core uses no OS services: the caller hands it the context (TLB, address space, and exit-request word) and the clock.

## FP and AdvSIMD

`src/interp/a64/simd_exec.zig` runs every FP and AdvSIMD kind. Arithmetic goes through `src/interp/softfloat.zig` with Arm's rules: FPCR's RMode, FZ, and DN; tininess detected before rounding; the positive default NaN; and signaling NaNs before quiet ones. Arm's FMAX and FMAXNM, its reciprocal estimates, and its saturating conversions are here. So results and FPSR's cumulative flags are the same bits on every host and in wasm.

FPCR.AHP isn't modeled: FCVT to and from half precision is always IEEE.

## System registers and the counter

| Register | MRS | MSR |
| --- | --- | --- |
| NZCV, FPCR, FPSR, TPIDR\_EL0 | Yes | Yes |
| TPIDRRO\_EL0 | Yes | |
| CNTFRQ\_EL0 | 24 MHz | |
| CNTVCT\_EL0 | The counter, below | |
| CTR\_EL0 | `0x8444c004` | |
| DCZID\_EL0 | 4 (`DC ZVA` zeroes 64 bytes) | |

`DC ZVA` zeroes its 64-byte block. `IC IVAU` drops what every vCPU decoded or compiled from its page, which a JIT writing code for another thread to run counts on ([jit.md](jit.md), Guest memory and the TLB). `DC CVAC`, `DC CVAU`, and `DC CIVAC` do nothing, and any other `SYS` is undefined.

**CNTVCT\_EL0** counts at 24 MHz: from the host's counter on arm64 hosts (scaled if the host's frequency differs), from `CLOCK_MONOTONIC` on Linux x86-64, and otherwise from instructions retired. With `H9_EMU_DETERMINISTIC=1` it's always instructions retired, so a program sees the same counter on every run and on both tiers.

## T1

ha64's front end is `src/jit/a64/`, on the shared layer in [jit.md](jit.md). T1 is the default on arm64 and x86-64 hosts, and on the web host, where `src/jit/wasm_t1.zig` compiles hot blocks to wasm as it does for h86 ([jit.md](jit.md), The web host). T0 there runs cold code to its eighth taken branch (`exec.runBranches`), so block heads come back to be counted.

**Regions** (`lift.zig`) are traces from the entry: straight-line code that follows `B` and `BL` to their targets when those aren't already in the region, falls through conditional branches, and stops after an indirect branch (`BR`, `BLR`, or `RET`), `SVC`, `BRK`, an undefined instruction, or at the limits: 512 instructions over at most two pages. Branch targets inside the region start blocks, and a backward one is a loop. Loop heads and the entry `poll`, so a chained loop sees a kick within one iteration.

**Lifted:** moves, arithmetic with and without flags, logical ops, shifts, bitfields, conditional select and compare, multiply and divide, every branch, loads and stores of one register or a pair (general and FP and SIMD registers, in every addressing mode), the exclusive and load-acquire and store-release forms, barriers, and the system registers EL0 reads. `STXR`, and `STXP` of W registers, are a branch on the monitor and a `cas`. LSE atomics, `STXP` of X registers, `LDXP`, `CLREX`, `DC ZVA`, `CNTVCT_EL0`, and the extensions run through `call.interp`.

**FP and AdvSIMD** (`lift_simd.zig`) lift to `fp.*` and `v.*` ops, which take the FP environment fixed when the region is lifted. FPCR is the guest's to change at any time, so a run of FPCR-dependent ops is a diamond: if RMode, FZ, DN, and AHP are all clear (Arm's default, and what every program here runs with), the lifted ops; otherwise `call.interp` for each instruction, so T0 applies the FPCR. The ops OR their exceptions into FPSR. A vector op on the low 64 bits (Q=0) zeroes the upper half, and vector FP ops are lifted only for Q=1, since computing all four lanes of a Q=0 op could raise exceptions from lanes the guest doesn't have. What isn't lifted runs through `call.interp`.

**Registers.** Within a block the lifter keeps each general register's latest value, read once and reused, and writes every result to the Cpu as it's made; the emitter's allocation keeps them in host registers and writes back only what's dirty, only where guest state must be exact.

**Flags** (`flags.zig`) are an `nzcv.*` value within a block, written to `Cpu.nzcv` (as a `pending.flags` the emitter writes only on the way out) before anything that can leave the region or look at the Cpu. Flags that the next instruction to touch them overwrites first aren't computed. On arm64 hosts NZCV lives in the host's NZCV, so `SUBS` and `B.cond` lower to themselves; on x86-64 hosts a condition on a compare's flags becomes an `icmp` of its operands.

## Copying instructions on arm64 hosts

On an arm64 host most guest instructions need no lowering: one that touches only registers runs correctly as itself if its register fields name the host registers holding the guest's. `src/jit/a64/copy.zig` makes such an instruction an IR `copy` op, whose register fields the arm64 emitter rewrites to wherever the allocator pinned the guest registers. It's on by default on arm64 hosts.

- **What qualifies:** an instruction that doesn't touch memory, branch, read the PC (`ADR`, `ADRP`), or touch system state, and whose read and write sets come only from its Rd, Rn, Rm, and Ra fields, with no register lists or implicit registers.
- **Which fields are registers** is found by probing the decoder: putting an unused register number in a field puts that register in the read or write set, which also gives its role. Register 31 is SP if the sets name SP, and otherwise ZR, which needs no mapping since the host's 31 is its own.
- **FP and AdvSIMD** copies run under the guest's FPCR and accumulate into FPSR. Guest V registers that only copies touch are pinned to host v16 and up for the region.

Elsewhere `ir_eval` runs a `copy` as `call.interp` on its word, so the region check covers copies on every host. Copying is what makes all of AdvSIMD, and bit-exact FP from the hardware, cost nothing per instruction on arm64 hosts.

## Memory order and atomics

arm64's memory model is weaker than both hosts', so ha64 needs no `Region.tso`.

- **Plain accesses** of up to 8 bytes, naturally aligned, are single-copy atomic, from a host access of the same size.
- **Exclusives:** `LDXR` records the address, size, and value in the monitor; `STXR` is a compare-and-swap against that value and succeeds only if it matches. Pairs are a wider compare-and-swap.
- **LSE atomics** are host atomics in T0, and `call.interp` in T1.
- **Barriers** and acquire and release accesses map one to one on arm64 hosts. x86-64 hosts are TSO, so they need fewer.

The litmus tests (`zig build litmus-a64`) check store buffering, message passing, and counters on every tier.

## Speed

Measured during development, before the branch merged:

- **Bench loop,** an arm64 guest on an x86-64 host: the 2-instruction loop of 10⁹ iterations ran in 0.67 s, about 3 G guest instructions/s, against Unicorn's 5.5 s on the same host.
- **FP loop** on an M3 Max: 3.1 ms median over 400 runs on T1, against 3 ms natively, once guest V registers stayed in host registers across the region.

- **In the browser,** the Linux demo page in headless Chromium on a 4-core x86-64 Linux VM: a busybox `sh` loop of 100,000 iterations took 7.4 s on T1 against 29 s on T0, `jq` summing 200,000 numbers 6.8 s against 26 s, and a `sqlite3` recursive query over 10⁶ rows 7.0 s against 47 s.

`zig build bench -Demu=zig` reports both tiers with T1's dispatch counts.

## Testing

- **Unit tests** in each file, including T0's against hand-assembled programs and `softfloat.zig` against TestFloat's vectors.
- **T0 against the hardware** on an arm64 Mac: `oracle_test.zig` runs random data-processing instructions natively in a small harness and on T0 from the same registers and flags, and `simd_oracle_test.zig` does the same for every FP and AdvSIMD class, with FPCR's RMode, FZ, and DN varied. `H9_SIMD_ORACLE=<count>[:<seed>]` runs more.
- **The region check** (`src/jit/check/a64.zig`): lifted regions against T0 from the same state ([jit.md](jit.md), Testing). The tracer (`src/jit/a64/tracer.zig`) runs a counted loop on T0, in `ir_eval`, natively, and in wasm, which must all end in the same state.
- **`zig build fuzz-a64`:** random valid programs (`src/jit/check/gen_a64.zig`) on T0 and T1 a region at a time, and against Unicorn in lockstep with `-Demu=unicorn`.
- **`zig build a64-jit`** runs the `[a64-jit]` cases in `tests/a64.zig` on T0 and T1: a store to a page of compiled code takes effect at the next instruction; a fault in a compiled region reports the exact PC and registers; a kick stops a compiled loop that makes no system calls; four `LDXR`/`STXR` threads, and four `LDADD` threads, lose no increments; unmapping a page another vCPU has cached faults its next access; a full code cache flushes while other vCPUs run; FP results and FPSR are the same bits on T0 and T1; and deterministic mode counts the same instructions on T0 and T1.
- **`zig build integration -Demu=zig`** runs the integration suite on ha64, and `-Djit-check` checks every region it compiles. `zig build integration -Dweb -Darch=arm64` runs it on the web host's ha64 under Node, and `zig build web-test` runs the Linux demo page on it in Chromium.
- **`zig build a64-inventory`** reports the arm64 instructions in binaries, for choosing what to lift next.
